DNS-Pinned Signer Identity for ThreatAttest

Status: Draft Proposal
Standards: RFC 4033/4034/4035, RFC 6698, RFC 7929, did:dns
Key type: secp256k1 (Cosmos-native)
DNS RR: TXT + URI (DNSSEC-signed)

This document proposes a method for cryptographically binding a ThreatAttest blockchain signer's identity to their DNS domain, secured with DNSSEC. The design draws on DKIM (RFC 6376), DANE/OPENPGPKEY (RFC 6698, 7929), SSHFP (RFC 4255), and the W3C did:dns method to create a robust, auditable, and rotatable identity anchor that the on-chain keeper can verify at publish time.

1. Abstract

A ThreatAttest attester currently proves control of a Cosmos address through the standard transaction-level secp256k1 signature and an additional message-level attester_sig. However, nothing in the current design verifiably links that address to a real-world organisational identity. An adversary can generate any number of fresh keypairs and publish attestations without any accountability anchor beyond on-chain reputation score.

This proposal adds a DNS identity layer: an attester publishes their secp256k1 public key (compressed, hex-encoded) in a DNSSEC-signed TXT record under a well-known sub-label of their domain. The on-chain keeper, or any off-chain verifier, can then:

  1. Resolve the DNS record (requiring DNSSEC validation to succeed)
  2. Verify that the public key in DNS matches the one used to produce attester_sig
  3. Confirm the domain is the same one recorded in the attestation's optional attester_domain field
  4. Award a DNS-pinned trust bonus to the attestation's computed trust score

The result is a three-anchor identity model: on-chain address + message signature + DNS-pinned public key, making Sybil attacks and key spoofing significantly harder.

2. Motivation

🔴 Current Problems

An attester's on-chain identity is pseudonymous — a bare Cosmos address. Anyone can generate a fresh keypair, acquire minimal TATST delegation (bypassing reputation gate), and begin publishing attestations with no accountability. A compromised or colluding attester is only punished retroactively via disputes.

🟢 DNS Pinning Provides

Domain ownership is a real-world accountability anchor — it costs money, leaves WHOIS records, and is logged by certificate transparency. A DNSSEC-signed key pin ties the attester's signing key to their internet identity, creating an auditable, rotatable, publicly inspectable record that cannot be forged without controlling the DNS zone.

The core insight borrowed from DKIM (RFC 6376) is that a public key published in DNS, under a domain the organisation controls, is self-certifying: the act of publishing it proves domain control, and DNSSEC proves the record hasn't been tampered with in transit. Applied to blockchain attesters, this gives consumers of threat intelligence a way to evaluate not just how much an attester has staked, but who they are.

ℹ️ Design Philosophy
DNS pinning is intentionally not a hard requirement for publishing attestations. It is a voluntary signal that earns an on-chain trust bonus and unlocks higher reputation tiers. This preserves permissionless participation while incentivising accountability.

4. DNS Record Schema

DNS

4.1 Primary TXT Record — Attester Key Pin

Modelled directly after DKIM's selector mechanism (RFC 6376 §3.6.1). The record owner is an attester-controlled domain. A selector (analogous to DKIM's key rollover mechanism) allows multiple keys to coexist during rotation.

Record Name Format

{selector}._tatkey.{domain}.

Example:
v1._tatkey.threatintel.example.com.      IN TXT  "…"
v2._tatkey.threatintel.example.com.      IN TXT  "…"    ; during rotation
active._tatkey.threatintel.example.com.  IN CNAME v1._tatkey.threatintel.example.com.

TXT Record Field Format

Fields are semicolon-separated key=value pairs, exactly matching DKIM's style (RFC 6376 §3.6.1). DNS TXT records may split content across multiple strings (each ≤255 bytes); verifiers MUST concatenate all strings before parsing. 

v1._tatkey.threatintel.example.com. 300 IN TXT (
    "v=TAT1; "
    "k=secp256k1; "
    "p=02a1b2c3d4e5f6...64hexchars...; "
    "a=cosmos1abc...xyz; "
    "n=ThreatIntel Example Corp; "
    "t=1710000000; "
    "exp=1741536000; "
    "h=sha256; "
    "flags=y"
)

Field Definitions

v=TAT1
Version tag. MUST be TAT1. Records with unknown versions MUST be ignored.
REQUIRED
k=secp256k1
Key algorithm. Currently only secp256k1 is defined (matching Cosmos SDK / ThreatAttest native key type). Reserved future values: ed25519, p256.
REQUIRED
p={pubkey}
Compressed secp256k1 public key, lowercase hex-encoded (66 characters = 33 bytes). This is the same key whose corresponding private key signs attester_sig in MsgPublishAttestation. If this field is empty (p=), the key is considered revoked.
REQUIRED
a={cosmos-addr}
The bech32 Cosmos address (cosmos1…) derived from this key. Verifiers confirm that SHA256(RIPEMD160(pubkey)) == decode(a). This cross-links the DNS record to the on-chain address explicitly.
REQUIRED
n={display-name}
Human-readable organisation or individual name. ASCII only, max 64 characters. Optional but strongly recommended for organisations.
OPTIONAL
t={unix-timestamp}
Unix timestamp of key publication. Allows verifiers to detect clock-skew attacks. The keeper enforces that t is within ±24h of the block time when verifying.
RECOMMENDED
exp={unix-timestamp}
Key expiry timestamp. Verifiers MUST reject records where exp is in the past. If omitted, default expiry is 1 year from t.
RECOMMENDED
h=sha256
Hash algorithm used when computing the attester signature payload digest. Currently only sha256 is supported.
OPTIONAL (default: sha256)
flags=y
Colon-separated flags. Defined values: y = testing / do not enforce, s = strict (fail-closed if DNS unavailable), r = rotation in progress (old key still valid). Example: flags=s:r
OPTIONAL
prev={selector}
Selector of the previous (now superseded) key. Used during rotation so verifiers can find the old key to verify older attestations signed with it.
OPTIONAL (during rotation)

4.2 Active Selector Pointer Record

To allow off-chain tools to discover the current key without knowing the selector, a stable CNAME (or TXT pointer) MUST point to the active selector: 

; Stable name — verifiers resolve this first
active._tatkey.example.com.  300  IN CNAME  v1._tatkey.example.com.

; Or as a TXT pointer if CNAME at non-apex is problematic:
_tatkey.example.com.  300  IN TXT  "active=v1"

4.3 Domain Verification Proof Record

To prove that the DNS record was published by the same entity who controls the Cosmos private key (and not an adversary who hijacked the DNS zone), the attester MUST publish a domain verification proof: a signature over the domain name, made with the same secp256k1 private key. 

; Proof record — the attester signs their own domain name
_tatproof.example.com.  300  IN TXT  (
    "v=TAT1; "
    "proof=; "
    "sel=v1"
)

The signed payload for the domain verification proof is:

// Payload = SHA-256 of: "tatkey-domain-proof|{domain}|{selector}|{cosmos-address}"
// e.g.: "tatkey-domain-proof|example.com|v1|cosmos1abc...xyz"
payload = SHA256("tatkey-domain-proof|" + domain + "|" + selector + "|" + cosmosAddr)
✅ Why This Matters
Without the proof record, a third party who controls a domain could copy someone else's public key into their own _tatkey TXT record. The proof record requires the private key to sign the specific domain name, making it impossible to copy without the key.

4.4 Optional: URI Record (did:dns Compatible)

For forward-compatibility with the W3C did:dns ecosystem and DIF Universal Resolver: 

; did:dns compatible URI record
_key1._did.example.com.  300  IN URI  100 10  "did:key:zQ3sh..."

; Where "did:key:zQ3sh..." is the secp256k1 key encoded as a did:key multibase string
; Algorithm prefix for secp256k1: 0xe7 (varint) → multibase base58btc → "zQ3s..."

5. DNSSEC Requirements

Security
🔴 Hard Requirement
All DNS-based identity claims in ThreatAttest MUST be protected by DNSSEC. A record that cannot be DNSSEC-validated MUST be treated as absent. Without DNSSEC, an attacker on the network path can inject arbitrary TXT records, defeating the entire identity-pinning scheme.

5.1 DNSSEC Validation Chain

Root (.) └── DNSKEY (KSK) + DS record ← Trust anchor (IANA / browser/OS built-in) └── com. / org. / net. / … └── DNSKEY (ZSK) └── example.com. ├── DNSKEY (ZSK for zone) ├── RRSIG for _tatkey TXT record ← Must be VALID ├── RRSIG for _tatproof TXT record ← Must be VALID └── NSEC3 records ← Prevents zone walking

5.2 Validation Algorithm

1
Query with DNSSEC (DO bit set)

The verifier MUST use a DNSSEC-validating resolver (e.g. Unbound, Google 8.8.8.8 with EDNS0 DO flag, Cloudflare 1.1.1.1). The DNS response MUST include RRSIG records for all relevant RRsets.

2
Validate RRSIG over TXT RRset

Verify the RRSIG signature covering the TXT RRset at {selector}._tatkey.{domain}. The RRSIG must chain up to a trusted DS record. The validation status MUST be SECURE (RFC 4035 §4.3).

3
Check denial of existence with NSEC/NSEC3

If the record does not exist, NSEC3 records (preferred over NSEC to prevent zone walking) MUST provide authenticated denial of existence. A missing record MUST be treated as identity not pinned.

4
Verify RRSIG expiry

RRSIG records have an Signature Expiration field. The verifier MUST check this against current wall-clock time. An expired RRSIG MUST be rejected even if cryptographically valid.

5
Parse and validate TXT field content

Only after DNSSEC validation passes, parse the TXT record fields. Verify: v=TAT1, k=secp256k1, p= not empty, exp not in past, cosmos address derivation check.

6
Verify domain proof signature

Fetch _tatproof.{domain}. Verify the secp256k1 signature in proof= against SHA256("tatkey-domain-proof|{domain}|{selector}|{cosmosAddr}"). This confirms the key owner controls both the DNS zone and the private key.

6. Key Types & Encoding

Cryptography

6.1 secp256k1 — Native ThreatAttest Key

ThreatAttest (Cosmos SDK) uses secp256k1 natively. The same key pair that signs Cosmos transactions signs the attester_sig payload. The DNS TXT record therefore carries the identical public key — no secondary key management is required. 

// Compressed secp256k1 public key: 33 bytes = 66 hex chars
// Prefix 0x02 (y even) or 0x03 (y odd), followed by 32 bytes x-coordinate
p=02a4b5c6d7e8f9001122334455667788990011223344556677889900aabbccddeeff01

// Cosmos address derivation (for cross-validation in field a=):
// 1. SHA-256(compressed_pubkey) → 32 bytes
// 2. RIPEMD-160(sha256_result) → 20 bytes
// 3. bech32 encode with prefix "cosmos" → cosmos1...

6.2 Key Encoding in DNS TXT

We evaluated three encodings for the p= field:

EncodingLength for 33 bytesReadabilityDecision
Hex (lowercase)66 charsEasy to inspect, copy, compare✅ RECOMMENDED — matches existing attester_sig convention in ThreatAttest
Base64 (standard)48 chars (+ padding)Compact; familiar from TLS/PGPAcceptable alternative
Base58~47 charsNo padding; URL-safe; Bitcoin/Cosmos nativeAcceptable if preferred
ℹ️ Hex chosen for ThreatAttest
Since attester_sig is already 128-char hex in the existing codebase, and artifact_sha256 is hex, we use hex throughout for consistency. The p= field is 66 hex characters (33 bytes compressed key).

8. Registration Flow

Operations
1
Generate or derive the secp256k1 keypair

The attester uses their existing Cosmos key. If registering a dedicated attestation key (recommended for organisations), generate a fresh keypair with a hardware wallet or HSM.

# Export compressed pubkey from Cosmos keyring
threatattestd keys show mykey --bech acc --pubkey
# Output: {"@type":"/cosmos.crypto.secp256k1.PubKey","key":"Aq..."} (base64)
# Convert to hex for DNS TXT field:
python3 -c "import base64,binascii; print(binascii.hexlify(base64.b64decode('Aq...')).decode())"
2
Choose a selector

Pick a selector string (e.g. v1, 2025a, yubikey1). The selector is part of the DNS record name and allows key rotation without disrupting existing attestations. Convention: use a date (20251001) or incrementing version.

3
Sign the domain proof

Compute and sign the domain proof payload with the secp256k1 private key:

# Payload to sign (UTF-8 encoded, SHA-256 hashed before signing)
payload = "tatkey-domain-proof|threatintel.example.com|v1|cosmos1abc...xyz"
# Sign with secp256k1 private key (same as attester_sig signing)
proof_sig = secp256k1_sign(SHA256(payload))
4
Publish DNS records

Add the following records to the DNS zone (use TTL 300–3600 seconds):

; Key pin record
v1._tatkey.threatintel.example.com.  300 IN TXT (
  "v=TAT1; k=secp256k1; "
  "p=02a4b5...01; "
  "a=cosmos1abc...xyz; "
  "n=ThreatIntel Example Corp; "
  "t=1710000000; exp=1741536000"
)

; Domain proof record
_tatproof.threatintel.example.com.  300 IN TXT (
  "v=TAT1; proof=aabb...ff; sel=v1"
)

; Active selector pointer
active._tatkey.threatintel.example.com.  300 IN CNAME
  v1._tatkey.threatintel.example.com.
5
Enable and verify DNSSEC signing

Ensure the zone is signed with DNSSEC (ECDSAP256SHA256 recommended). Verify using:

# Verify DNSSEC chain for the TXT record
dig +dnssec +multi v1._tatkey.threatintel.example.com. TXT
# Must show: RRSIG, flags: qr rd ra ad (ad = Authenticated Data)

# Check DS record is published at parent zone
dig +dnssec DS threatintel.example.com. @a.gtld-servers.net.

# End-to-end DNSSEC validation (using drill)
drill -TD v1._tatkey.threatintel.example.com. TXT
6
Register attester_domain on-chain

Submit a MsgRegisterAttesterDomain transaction (new message — see §10) specifying the domain and selector. The keeper verifies the DNS record at submission time and stores the domain binding on-chain.

threatattestd tx attestation register-domain   --domain "threatintel.example.com"   --selector "v1"   --from mykey   --chain-id threatattest-1

9. Verification Flow

9.1 On-Chain Verification (Keeper)

When MsgPublishAttestation is received and the attester has a registered domain, the keeper performs DNS verification as part of message processing:

(keeper.GetAttesterDomain(ctx, attester)) ├── No → proceed without DNS bonus (trust score unaffected) └── Yes ──────────────────────────────────────────────────┐ │ 3. Is DNS check cache fresh? (< 1 epoch = 30 min) │ ├── Yes (cached VALID) → apply DNS bonus, continue │ └── No → perform live DNS lookup │ │ │ 4. 9.2 Off-Chain Verification (Browser Extension / API Client)

The ThreatAttest browser extension and any API client can independently verify DNS pinning without trusting the node: 

// In the browser extension (src/api.js)
async function verifyDNSPin(attester, domain, selector, pubkeyHex) {
  // Use DoH (DNS over HTTPS) for browser context
  const dohURL = `https://cloudflare-dns.com/dns-query?name=${selector}._tatkey.${domain}&type=TXT`;
  const res = await fetch(dohURL, { headers: { Accept: 'application/dns-json' } });
  const data = await res.json();

  // Check DNSSEC validated (AD flag in DoH response)
  if (!data.AD) return { valid: false, reason: 'DNSSEC not validated' };

  // Parse TXT fields
  const txt = data.Answer?.find(r => r.type === 16)?.data || '';
  const fields = parseTATKeyRecord(txt);

  // Verify pubkey matches
  if (fields.p !== pubkeyHex) return { valid: false, reason: 'pubkey mismatch' };

  // Verify cosmos address derivation
  if (deriveCosmosAddr(fields.p) !== attester) return { valid: false, reason: 'address mismatch' };

  // Check expiry
  if (fields.exp && parseInt(fields.exp) < Date.now() / 1000)
    return { valid: false, reason: 'key expired' };

  return { valid: true, name: fields.n || domain };
}

10. Key Rotation

Operations

Key rotation is the most operationally sensitive part of any pinning scheme. We adopt DKIM's selector-based rotation model, which allows old and new keys to coexist during a transition window.

10.1 Rotation Procedure

1
Publish new key under a new selector (pre-publish phase)

Add the new key TXT record at least 2× DNS TTL before switching (minimum 10 minutes). This ensures resolvers worldwide have cached the new key before it becomes active.

# New key published BEFORE switching
v2._tatkey.example.com.  300 IN TXT "v=TAT1; k=secp256k1; p=03new...; a=cosmos1new...; t=...; flags=r"
_tatproof.example.com.   300 IN TXT "v=TAT1; proof=new_proof_sig; sel=v2"
2
Submit MsgRotateAttesterKey on-chain

Broadcast the rotation transaction, which is signed by BOTH old and new keys (dual-sig rotation, prevents hijacking). The keeper updates the on-chain domain record and sets a rotation window of 72 hours during which both keys are valid.

threatattestd tx attestation rotate-key   --domain "example.com"   --new-selector "v2"   --old-selector "v1"   --from mykey-v1 \         # old key signs
  --new-pubkey 03new...     # new pubkey for verification
3
Switch active pointer

Update the active CNAME to point to the new selector. Old attestations signed with the old key remain valid (they carry the selector in attester_domain_selector) and can still be verified using the old key record.

active._tatkey.example.com.  300 IN CNAME  v2._tatkey.example.com.
# Old record remains for 72h rotation window, then can be removed
4
Retire old key after rotation window

After 72 hours (or the configured rotation window), remove the old TXT record or replace it with an empty p= to signal revocation. Update prev=v1 in the new record so verifiers know to look for the old key when verifying pre-rotation attestations.

11. Key Revocation

Security

Revocation is critical when a private key is compromised. Unlike rotation (orderly planned change), revocation must be instant and fail-closed.

11.1 DNS-Level Revocation

Set p= (empty) in the TXT record. Verifiers MUST treat an empty p= field as explicit revocation, immediately stop accepting attestations from this key, and flag all existing ACTIVE attestations signed by this key as DISPUTED. 

; Emergency revocation — empty p= field signals key compromise
v1._tatkey.example.com.  60 IN TXT "v=TAT1; k=secp256k1; p=; a=cosmos1abc...xyz"
; TTL set to 60s for rapid propagation

11.2 On-Chain Revocation

Submit MsgRevokeAttesterDomain on-chain (new message). The keeper immediately:

  1. Marks all ACTIVE attestations from this attester as DISPUTED
  2. Removes the DNS domain binding from the attester record
  3. Reduces reputation score by a configurable penalty (default: −50 RS)
  4. Emits an EventAttesterKeyRevoked event for indexers

11.3 Emergency Revocation Without Private Key

If the private key is lost/stolen and the attester cannot sign a revocation tx:

⚠️ Social Recovery Path
The attester updates the DNS zone (using DNS zone credentials, separate from the signing key) to set p= (empty). The on-chain keeper, during its next DNS health-check (every epoch = ~30 min), detects the revocation and auto-applies it. This provides a ~30 minute worst-case revocation window using only DNS credentials.

12. Cross-Chain & Multi-Domain Pinning

12.1 Multi-Domain Attesters

Large organisations may have multiple domains. Each domain may pin the same key (using identical p= fields) or different keys. The on-chain attester record supports a list of verified domains: 

// AttesterDomainRecord — stored on-chain per attester
type AttesterDomainRecord struct {
    Attester    string          // cosmos1… address
    Domains     []DomainPin     // all verified domain pins
    PrimaryDomain string        // canonical identity domain
    VerifiedAt  int64           // last DNS verification block height
}

type DomainPin struct {
    Domain     string   // e.g. "threatintel.example.com"
    Selector   string   // e.g. "v1"
    PubKeyHex  string   // cached compressed pubkey from DNS
    VerifiedAt int64
    ExpiresAt  int64
}

12.2 Cross-Chain Attestation References

A ThreatAttest attester may also want to reference their identity on other blockchains. The _tatkey TXT record supports an optional chains= field: 

v1._tatkey.example.com. 300 IN TXT (
  "v=TAT1; k=secp256k1; p=02...; a=cosmos1...; "
  "chains=ethereum:0xABCD...;bitcoin:bc1q...;solana:ABC..."
)
; Format: "chains={chain}:{address};{chain}:{address};..."
; Each chain address independently verifiable via its own key derivation

Cosmos SDK

13.1 New Module: x/dnsidentity (or extension to x/attestation)

    RotationHistory []string `json:"rotation_history"`  // past selectors
    Status          DNSIDStatus `json:"status"`
}

type DNSIDStatus int32
const (
    DNSIDStatus_UNVERIFIED DNSIDStatus = 0
    DNSIDStatus_ACTIVE     DNSIDStatus = 1  // DNS check passed
    DNSIDStatus_EXPIRED    DNSIDStatus = 2  // exp= in past
    DNSIDStatus_REVOKED    DNSIDStatus = 3  // p= empty detected
    DNSIDStatus_UNREACHABLE DNSIDStatus = 4 // DNS query failed
)

13.5 Keeper Changes

// In keeper/msg_server.go — PublishAttestation handler
func (k Keeper) PublishAttestation(ctx Context, msg *MsgPublishAttestation) (*MsgPublishAttestationResponse, error) {
    // … existing validation …

    // NEW: DNS identity verification
    if msg.AttesterDomain != "" {
        dnsRecord, err := k.GetDNSIdentityRecord(ctx, msg.Attester)
        if err == nil && dnsRecord.Status == DNSIDStatus_ACTIVE {
            // Cached verification still fresh (within 1 epoch)
            if ctx.BlockHeight()-dnsRecord.VerifiedAt < BlocksPerEpoch {
                rec.DNSVerified = true
                rec.DNSIdentityDomain = msg.AttesterDomain
            } else {
                // Cache stale — trigger async re-verification via ABCI
                k.EnqueueDNSVerification(ctx, msg.Attester, msg.AttesterDomain, msg.AttesterSelector)
            }
        }
    }

    // … store record …
}

// In abci/abci.go — EndBlock hook for DNS re-verification
func EndBlock(ctx Context, k Keeper) {
    queue := k.GetDNSVerificationQueue(ctx)
    for _, job := range queue {
        result := k.PerformDNSVerification(ctx, job)  // live DNS query
        k.UpdateDNSIdentityRecord(ctx, result)
        k.EmitDNSVerificationEvent(ctx, result)
    }
}

13.6 Trust Score Delta

DNS verification adds a bonus to the computed trust score. The formula extension: 

// Existing formula:
// TrustScore = (SeverityWeight × ConfidenceFraction × EndorseFactor × TierWeight) × 1000

// NEW: DNS pinning multiplier
func TrustScore(severity, confidence, endorsements, attesterRS uint32, dnsVerified bool) uint32 {
    base := existingTrustScore(severity, confidence, endorsements, attesterRS)

    if dnsVerified {
        // Apply DNS bonus: flat +200 points, capped at 1000
        bonus := uint32(200)
        if base + bonus > 1000 {
            return 1000
        }
        return base + bonus
    }
    return base
}

15. Attack Vectors & Response Procedures

15.1 Zone Compromise Response

🚨 Incident Response: DNS Zone Compromise
  1. Immediately set p= (empty) in all _tatkey TXT records
  2. Within 30 minutes, the keeper's epoch DNS health-check detects the revocation
  3. Separately, submit MsgRevokeAttesterDomain if private key access is available
  4. Regain zone control, generate a new keypair, publish under a new selector
  5. Submit MsgRegisterAttesterDomain with the new key
  6. Review all attestations published during the compromise window via governance dispute

15.2 Key Compromise Response

🚨 Incident Response: Signing Key Compromise
  1. Update DNS to set p= (empty) using DNS zone credentials — stops DNS bonus and triggers keeper auto-revocation within one epoch
  2. If tx-signing key still available: submit MsgRevokeAttesterDomain immediately
  3. Rotate to a new keypair (new Cosmos address). The old address's reputation is penalised and domain unlinked
  4. Publish new key under a new selector; submit MsgRegisterAttesterDomain

20. Summary

This proposal defines a complete, standards-grounded method for pinning ThreatAttest attester identity to DNS using DNSSEC. The design draws from the proven DKIM selector model for key publication and rotation, the DANE/OPENPGPKEY framework for DNS-based key discovery, and the W3C did:dns method for forward compatibility with decentralised identity ecosystems.

The key innovations specific to ThreatAttest are the domain verification proof (a secp256k1 signature over the domain name that cross-links the DNS zone to the private key), the on-chain keeper integration (automatic DNS health-checks every epoch, cache, auto-revocation), and the trust score bonus that incentivises voluntary adoption without making DNS pinning a hard gate.

Combined with multi-validator DNS consensus (vote extensions) and a transparency event log, the system provides a robust, auditable identity layer that is resistant to the main attack vectors (cache poisoning is defeated by DNSSEC; zone compromise is mitigated by the proof signature; key compromise is mitigated by rapid epoch-based auto-revocation via DNS update).
