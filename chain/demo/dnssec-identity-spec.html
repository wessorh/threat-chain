DNSSEC-Anchored Signer Identity
Protocol Specification

A complete protocol for cryptographically binding a ThreatAttest signer identity to a DNSSEC-secured domain name, including on-chain self-publication of the identity block, the domain-to-key proof, and domain-referenced attestation publishing.

Document: TAT-IDP-001 Status: Proposed Standard Chain: threatattest-1 Module: x/identity (new)

S1 Abstract

This document specifies the ThreatAttest Identity Delegation Protocol (TAT-IDP), a method for cryptographically binding a ThreatAttest blockchain signing address to a domain name secured by DNSSEC. The binding is established through three mutually-authenticating anchors: a secp256k1 public key published in a DNSSEC-signed DNS TXT record, an on-chain identity block self-published by the key holder, and a domain-proof signature that prevents substitution attacks.

Once registered, a signer's attestations carry a domain reference field (attester_domain) that consumers can independently verify against both the DNS record and the chain state. This transforms anonymous blockchain addresses into auditable, domain-backed identities while preserving the signer's ability to operate pseudonymously if the underlying domain is privacy-protected.

The protocol defines the full lifecycle: initial registration, self-publication transaction, incremental trust accumulation, key rotation using a DKIM-style selector model, and revocation via both DNS and on-chain mechanisms.

S2 Motivation & Goals

The Sybil Problem in Decentralised Threat Intelligence

A threat intelligence blockchain where attestations carry equal weight regardless of publisher creates a Sybil attack surface: an adversary can register thousands of fresh addresses and flood the chain with coordinated false positives or false negatives at negligible cost. Staking-based reputation systems raise the economic cost but do not solve attribution. What is missing is a persistent, externally verifiable identity anchor that ties each signer to an accountable real-world entity.

Why DNS and DNSSEC?

DNS is the identity layer of the Internet. Domain registration requires real-world accountability. DNSSEC adds cryptographic data-origin authentication, making it impossible to fabricate a DNS response without control of the zone's private signing key. Publishing an attester's public key in a DNSSEC-signed TXT record creates a binding that is externally verifiable, accountable, non-duplicable, revocable, and standardised.

Design Goals

  1. Mutual authentication - The DNS record proves key ownership of the domain; the chain record proves the domain is claimed by that address; the domain-proof signature proves the chain address holder controls the DNS.
  2. Self-sovereignty - No trusted third party or oracle is required. The signer self-publishes their identity block in a single transaction.
  3. Composability - Attestations reference the domain by name; identity resolution is a separate, cacheable operation.
  4. Privacy preserving - The binding can use a privacy-proxy domain. The protocol does not require the registrant identity to be public.
  5. Incremental adoption - Domain binding is optional. Anonymous attesters continue to function; domain-bound attesters receive a trust score bonus and a compliance tier upgrade.

S4 Protocol Overview

The Three-Anchor Identity Model

🔑

Anchor 1 - DNS

Public key published at {selector}._tatkey.{domain} in a DNSSEC-signed TXT record. Proves the key holder controls the DNS zone.

⛓️

Anchor 2 - Chain

Identity block self-published in a signed MsgRegisterIdentity transaction. Proves the chain address holder accepts the domain binding.

✊

Anchor 3 - Proof Sig

secp256k1 signature over a canonical domain-proof payload, published at _tatproof.{domain}. Closes the cross-authentication loop.

What Each Anchor Proves

AnchorWhat it provesWhat it does NOT prove
DNS TXT recordThe holder of the domain's zone-signing key authorized this public key to be associated with this domain. DNSSEC guarantees the record has not been tampered with in transit.Does not prove the domain holder IS the chain address holder. An adversary who only controls DNS could publish someone else's public key.
On-chain identity blockThe holder of the secp256k1 private key corresponding to the chain address claims this domain as their identity.Does not prove the chain key holder controls the domain's DNS. A relay could re-broadcast a stolen transaction with a different domain.
Domain proof signatureThe holder of the chain's secp256k1 key produced a signature over a payload that includes the domain name and their cosmos address. Published in DNS at the domain.Does not prove the key holder is a specific human or organization - only that one entity controls both the DNS zone and the private key.

Together, the three anchors establish a proof of co-control: a single entity controls both the DNS zone and the signing key. This is the strongest practically achievable binding without a trusted third party.

S7 Identity Binding Model

The binding between the three anchors is established by the following mathematical relationships:

Let:
  K   = secp256k1 keypair (private_key, public_key)
  A   = CosmosAddress( public_key )   // deterministic: RIPEMD160(SHA256(pubkey))
  D   = identity domain (e.g. "security.acme.com")
  S   = selector string (e.g. "k2025a")

Anchor 1 (DNS):
  TXT record at {S}._tatkey.{D} contains:
    p = hex( compress( public_key ) )        // proves key ownership
    a = bech32( A )                          // binds key to chain address
  Record is signed by zone DNSSEC key        // proves domain control

Anchor 2 (Chain):
  MsgRegisterIdentity signed by private_key:
    domain    = D                            // claims domain ownership
    selector  = S                            // references DNS record
    pubkey_hex = hex( compress(public_key) ) // must match DNS p= field
  Transaction signature = sign(tx_hash, private_key) // proves key possession

Anchor 3 (Domain Proof):
  domain_proof_payload = SHA256(
      "tatkey-domain-proof"
      + "|" + D
      + "|" + S
      + "|" + bech32(A)
      + "|" + registered_at_unix_str
  )
  domain_proof_sig = secp256k1_sign( domain_proof_payload, private_key )
  Published at _tatproof.{D} AND included in MsgRegisterIdentity

Verification passes if ALL of:
  secp256k1_verify( domain_proof_payload, domain_proof_sig, public_key ) == true
  DNS TXT {S}._tatkey.{D} resolves AND DNSSEC validates
  DNS TXT record contains p= hex(public_key)
  DNS TXT record contains a= bech32(A)
  tx.signer == A  (enforced by Cosmos SDK ante handler)

The circular dependency between the three anchors means that an adversary who controls only one anchor cannot construct a valid registration. All three must be under common control simultaneously.

S8 Domain Proof Payload Construction

// Step 1: Construct the canonical message string
func BuildDomainProofPayload(
    domain       string,  // normalised: lowercase, no www, no trailing dot
    selector     string,  // exact selector string
    cosmosAddr   string,  // full bech32 cosmos address
    registeredAt int64,   // Unix timestamp as decimal
) []byte {
    msg := fmt.Sprintf(
        "tatkey-domain-proof|%s|%s|%s|%d",
        domain, selector, cosmosAddr, registeredAt,
    )
    // Step 2: SHA-256 hash the message
    h := sha256.Sum256([]byte(msg))
    return h[:]
}

// Step 3: Sign with secp256k1 private key (compact 64-byte format)
// sig = secp256k1_sign_compact( payload_hash, private_key )
// Encode as 128-char lowercase hex string for DNS/chain storage

Example

// Inputs:
domain      = "security.acme.com"
selector    = "k2025a"
cosmosAddr  = "tatst1qvzryktygq9abcdef..."
registeredAt = 1720000000

// Message string:
"tatkey-domain-proof|security.acme.com|k2025a|tatst1qvzryktygq9abcdef...|1720000000"

// SHA-256 hash (hex, 64 chars):
"3f9c1a2b4e5d6f..."

// secp256k1 compact signature (hex, 128 chars):
"3045022100d4e5f6..."

// Published in DNS at _tatproof.security.acme.com:
"v=TAT1 sel=k2025a proof=3045022100d4e5f6... t=1720000000"
✅
Timestamp binding prevents replay attacksThe registered_at timestamp is included in the proof payload. A stolen proof signature cannot be used to register a new identity with a different timestamp - the payload would hash differently, invalidating the signature.

S9 Self-Publication Flow

The identity block is self-published - no privileged administrator or oracle is required. The attester performs these steps in sequence:

Generate or identify the signing keypairUse the existing Cosmos SDK keyring key. No new key is needed - the DNS record binds the existing chain key to a domain.
threatattestd keys show mykey --bech acc
# output: tatst1qvzryktygq9abcdef...

threatattestd identity pubkey-hex mykey
# output: 02a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2
Choose a selector stringAny alphanumeric string 1-32 characters. Convention: k{year}{letter} (e.g. k2025a). Selectors MUST NOT contain underscores (used as label separators in the FQDN).
Determine the registration timestampUse current Unix time. The timestamp MUST be within +/- 600 seconds of the chain block time when the transaction is processed.
date +%s
# output: 1720000000
Compute and sign the domain proof payload
threatattestd identity sign-domain-proof \
    --domain   security.acme.com \
    --selector k2025a \
    --addr     tatst1qvzryktygq9abcdef... \
    --ts       1720000000 \
    --from     mykey
# output:
# domain_proof_sig: 3045022100d4e5f6... (128 hex chars)
# proof_payload:    3f9c1a2b4e5d6f... (64 hex chars, pre-sign hash)
Publish the TAT Key Record in DNSAdd TXT record at k2025a._tatkey.security.acme.com. Ensure DNSSEC is enabled. Wait for propagation.
; Zone file entry:
k2025a._tatkey.security.acme.com. 3600 IN TXT \
    "v=TAT1 k=secp256k1 p=02a1b2... a=tatst1qvz... n=Acme Security t=1720000000 exp=1751536000"
Publish the Domain Proof Record in DNSAdd TXT record at _tatproof.security.acme.com with TTL 300s.
_tatproof.security.acme.com. 300 IN TXT \
    "v=TAT1 sel=k2025a proof=3045022100d4e5f6... t=1720000000"
Submit MsgRegisterIdentity to the chain
threatattestd tx identity register \
    --domain           security.acme.com \
    --selector         k2025a \
    --pubkey-hex       02a1b2c3d4e5f6... \
    --domain-proof-sig 3045022100d4e5f6... \
    --registered-at    1720000000 \
    --display-name     "Acme Security Research" \
    --contact-uri      "https://security.acme.com" \
    --from             mykey \
    --chain-id         threatattest-1 \
    --fees             2000utatst

    // MUST be within +/-600s of the block time.

S12 Verification Algorithm

12.1 Keeper-Side Verification (at registration)

func VerifyIdentityRegistration(ctx Context, msg MsgRegisterIdentity) error {

    // Phase 1: Structural validation (ValidateBasic)
    if err := msg.ValidateBasic(); err != nil { return err }

    // Phase 2: Domain proof signature verification
    payload := BuildDomainProofPayload(
        msg.Domain, msg.Selector, msg.Attester, msg.RegisteredAt,
    )
    if !secp256k1.Verify(payload, msg.DomainProofSig, msg.PubkeyHex) {
        return ErrInvalidDomainProofSig
    }

    // Phase 3: DNS resolution
    fqdn := fmt.Sprintf("%s._tatkey.%s", msg.Selector, msg.Domain)
    var txtRecord string
    var dnssecValid bool

    if msg.DNSEvidence != nil {
        // Fast path: use attester-supplied evidence (verified in-block)
        txtRecord, dnssecValid = VerifyDNSEvidence(msg.DNSEvidence, fqdn)
    } else {
        // Slow path: defer to epoch resolver (status stays PENDING)
        return setPending(ctx, msg)
    }

    if !dnssecValid { return ErrDNSSECValidationFailed }

    // Phase 4: TXT record content verification
    parsed := ParseTATKeyRecord(txtRecord)

    if parsed.Version != "TAT1"       { return ErrTATRecordVersionMismatch }
    if parsed.KeyType != "secp256k1"  { return ErrUnsupportedKeyType }
    if parsed.P != msg.PubkeyHex      { return ErrPubkeyMismatch }
    if parsed.A != msg.Attester       { return ErrAddressMismatch }
    if parsed.Exp < ctx.BlockTime()   { return ErrTATRecordExpired }

    // Phase 5: Store identity record
    rec := DNSIdentityRecord{
        ID:             ComputeIdentityID(msg.Attester, msg.Domain, msg.RegisteredAt),
        CosmosAddress:  msg.Attester,
        Domain:         msg.Domain,
        Selector:       msg.Selector,
        PubkeyHex:      msg.PubkeyHex,
        DomainProofSig: msg.DomainProofSig,
        DNSProofTXTName: fmt.Sprintf("_tatproof.%s", msg.Domain),
        DisplayName:    msg.DisplayName,
        ContactURI:     msg.ContactURI,
        RegisteredAt:   msg.RegisteredAt,
        ExpiresAt:      msg.RegisteredAt + msg.TTLSeconds,
        LastVerifiedAt: ctx.BlockTime().Unix(),
        BlockHeight:    ctx.BlockHeight(),
        Status:         DNSIDStatus_ACTIVE,
        DNSSECAlgorithm: parsed.DNSSECAlgorithm,
        DNSSECKeyTag:   parsed.DNSSECKeyTag,
    }
    SetIdentityRecord(ctx, rec)

    // Phase 6: Reputation reward
    repKeeper.AddReputation(ctx, msg.Attester, 200)

    // Phase 7: Emit event
    ctx.EventManager().EmitEvent(sdk.NewEvent(
        EventTypeIdentityRegistered,
        sdk.NewAttribute(AttributeKeyCosmosAddr, msg.Attester),
        sdk.NewAttribute(AttributeKeyDomain, msg.Domain),
        sdk.NewAttribute(AttributeKeySelector, msg.Selector),
        sdk.NewAttribute(AttributeKeyIdentityID, rec.ID),
    ))

    return nil
}

S13 DNSSEC Requirements

🚫
DNSSEC is mandatory - not optionalA domain without DNSSEC can be hijacked via DNS cache poisoning (Kaminsky attack) or BGP hijacking of the authoritative name server. An attacker who can spoof DNS can substitute a fraudulent public key in the TXT record. Without DNSSEC, the DNS anchor provides zero security guarantee.

Required Zone Configuration

  • The zone MUST be signed with DNSSEC.
  • The zone MUST have a DS record in the parent zone (delegation established).
  • TXT records for _tatkey and _tatproof subdomains MUST be covered by RRSIG records.
  • The NSEC/NSEC3 chain MUST cover the _tatkey and _tatproof labels.
  • DNSSEC signatures MUST NOT be expired at the time of registration.

S14 DNSSEC Validation Chain

+----------------------------------------------------------+ | ICANN Root Trust Anchor | | KSK Algorithm 8 (RSA/SHA-256) | | Key Tag: 20326 (built into all resolvers) | +--------------------------+-------------------------------+ | DS record in "." zone v +----------------------------------------------------------+ | TLD Zone (e.g. .com) | | Signed by .com DNSKEY / ZSK | +--------------------------+-------------------------------+ | DS record in .com zone v +----------------------------------------------------------+ | acme.com Zone | | DNSKEY (KSK + ZSK) | | DS hash published in .com parent zone | +--------------------------+-------------------------------+ | Delegation (if subdomain zone) v +----------------------------------------------------------+ | security.acme.com Zone (or inline in acme.com) | | RRSIG over TXT RRset | +--------------------------+-------------------------------+ | RRSIG TXT v +----------------------------------------------------------+ | k2025a._tatkey.security.acme.com IN TXT "v=TAT1 ..." | | RRSIG TXT ... (signed by zone ZSK) | +----------------------------------------------------------+

Each link in the chain is validated: ICANN root to TLD to registered domain to (optional subdomain delegation) to TXT record RRSIG. Any missing or invalid link causes rejection.

S16 Key Rotation

Key rotation allows an attester to replace their signing key while maintaining continuity of their domain identity, using a DKIM-style dual-selector handoff:

TIME ---------------------------------------------------------------> Old key (k2025a): ####################################...................... |<--- active ------------------->|overlap| inactive New key (k2025b): ....................|################################### |<-- pre-pub ----->|<------ active ----------------> DNS: k2025a._tatkey.domain -> old pubkey (flags: ROTATE_PENDING=1) k2025b._tatkey.domain -> new pubkey (published before rotation) _tatkey.domain TXT sel= k2025a -> k2025b (updated atomically) Chain: MsgRotateIdentityKey submitted with old key sig + new key sig Old identity record: status = SUPERSEDED New identity record: status = ACTIVE, prev_identity_id = old ID Overlap period: minimum 2x DNS TTL (recommended 2+ hours) Old key removed from DNS: after confirming new key is ACTIVE

S17 Revocation

17.1 Voluntary Revocation

type MsgRevokeIdentity struct {
    Attester  string `json:"attester"`
    Reason    string `json:"reason,omitempty"`  // max 256 bytes
    RemoveDNS bool   `json:"remove_dns"`        // advisory: attester will remove DNS record
}

The keeper immediately sets status = REVOKED and emits EventIdentityRevoked. Future attestations from this address referencing the revoked domain are rejected. Existing attestations are not retroactively affected.

17.2 Automatic Revocation via DNS Polling

// EndBlock epoch hook - runs every ~1 hour
for each identity in GetActiveIdentities() {
    txt, valid := ResolveDNSSEC(identity.Selector, identity.Domain)
    switch {
    case !valid || txt == "":
        // DNS record removed or DNSSEC broken
        identity.Status = DNSIDStatus_DNS_REMOVED
        repKeeper.SubReputation(ctx, identity.CosmosAddress, 200)
    case parsed.P == "":
        // Empty p= field signals DNS-level revocation
        identity.Status = DNSIDStatus_REVOKED
        repKeeper.SubReputation(ctx, identity.CosmosAddress, 200)
    case identity.ExpiresAt < ctx.BlockTime().Unix():
        identity.Status = DNSIDStatus_EXPIRED
    default:
        identity.LastVerifiedAt = ctx.BlockTime().Unix()
    }
    SetIdentityRecord(ctx, identity)
}

17.3 DNS-Level Revocation Signal

Setting p= (empty) in the TAT Key Record signals DNS-level revocation:

k2025a._tatkey.security.acme.com. 300 IN TXT "v=TAT1 k=secp256k1 p= a=tatst1... t=1720000000 exp=1720000000"
                                                                      ^-- empty p= = REVOKED

The epoch resolver detects the empty p= within approximately one epoch (~1 hour) and transitions identity status to REVOKED.

S18 Expiry & Renewal

type MsgRenewIdentity struct {
    Attester        string `json:"attester"`

Renewal re-validates the DNS binding with fresh DNSSEC evidence and resets ExpiresAt = now + TTLSeconds. The RegisteredAt field and ID remain unchanged to preserve the audit trail.

⏰
Renewal timingIdentities SHOULD be renewed at least 7 days before expiry. The keeper emits EventIdentityExpiryWarning at 7-day and 1-day marks. The CLI provides an "identity status" command showing remaining time and renewal reminder.

S25 Attack Vectors & Mitigations

AttackPreconditionMitigation
Forge a DNS TXT record Control of the DNS zone or DNS cache poisoning DNSSEC is mandatory. Cache poisoning defeated by data-origin authentication. Zone compromise requires DNSSEC key theft - store KSK in hardware HSM.
Replay a stolen domain proof signature Intercept the domain proof from DNS Proof payload includes registered_at timestamp. Keeper enforces +/-600s tolerance. A replayed proof with a different timestamp fails signature verification.
Cross-chain address substitution Attacker replaces cosmos address in DNS with their own Keeper verifies CosmosAddress(pubkey_hex) == msg.Attester. Only one address can correspond to any given public key.
Domain squatting after revocation Attacker registers the domain after the original owner revokes Domain-to-address mapping is freed only after revocation + 24h cooling-off period. Domain transfer requires new registrar evidence chain.
Sybil attack via cheap subdomains Attacker registers many subdomains of one domain Each subdomain is a separate identity. Registration fee applies per identity. The parent domain owner controls all subdomain DNS, so subdomains under one registrant still map to one accountable entity.
BGP hijack of authoritative nameserver Attacker hijacks IP of authoritative DNS server DNSSEC validation does not rely on network path integrity. DNSSEC signatures are verified cryptographically regardless of which server responds.
Key theft + domain proof replay Both private key AND domain proof signature are stolen Attacker still cannot change the registered_at timestamp in the proof without invalidating the signature. Old registrations are immutable. Rotation with new key immediately supersedes stolen key.
DoH resolver compromise Attacker controls the DoH resolver used by the keeper Keeper queries multiple DoH endpoints (Cloudflare + Google by default). Governance can add more. Attester-supplied DNSEvidence bundle provides an alternative path that bypasses keeper DNS resolution entirely.

// ComputeIdentityID returns the deterministic record identifier
func ComputeIdentityID(cosmosAddr, domain string, registeredAt int64) string {
    data := fmt.Sprintf("%s|%s|%d", cosmosAddr, domain, registeredAt)
    h := sha256.Sum256([]byte(data))
    return hex.EncodeToString(h[:])
}
